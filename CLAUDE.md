# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Android port of the FIPS mesh daemon, embedded in a `VpnService` app. A Rust JNI shim (`shim/`) runs the fips node in-process; the Kotlin app (`android/`) provides the VPN tunnel, per-app split tunnel, and Material 3 UI. Selected apps reach the mesh over `fd00::/8` with `.fips` DNS while keeping normal internet through a userspace forwarder.

## Build & test commands

```bash
# Rust shim → android/app/src/main/jniLibs/<abi>/libfips_android.so
./build-native.sh                # all ABIs: arm64-v8a, armeabi-v7a, x86_64
./build-native.sh arm64-v8a      # single ABI for faster iteration

# Host-side Rust tests (engine lifecycle, DNS proxy, packet codecs — everything but the JNI surface)
source ./android-env.sh && (cd shim && cargo test)
# Single test: (cd shim && cargo test dns::tests::name_of_test)

# Two-node host smoke test of the embedding seam
source ./android-env.sh && (cd smoke && cargo run)

# APK (debug; toolchain paths are machine-specific — see android/local.properties)
cd android && JAVA_HOME=~/.local/jdk-17 ~/.local/gradle-8.7/bin/gradle assembleDebug
# → app/build/outputs/apk/debug/app-debug.apk; install with adb install

# Release: one signed APK per ABI + sha256 + unstripped .so → dist/v<versionName>/
./release-build.sh                # all ABIs; or pass a subset, e.g. arm64-v8a
```

`source ./android-env.sh` is required before any cargo command:
- Cross builds: sets the NDK r27c linker/CC/AR (API 24 floor — `getifaddrs` in fips's STUN code).
- **Host builds too**: it pins `LIBCLANG_PATH=/usr/lib/llvm-18/lib`, overriding a machine-wide ESP32/Xtensa libclang that breaks bindgen (`rustables`) with an `assertion failed 4 != 8` panic. The override is deliberately unconditional (an already-set `LIBCLANG_PATH` loses) — point elsewhere with `FIPS_LIBCLANG_PATH`, as CI does.
- Both machine paths have env overrides so the script needs no editing off this machine: `FIPS_NDK_HOME` (NDK location) and `FIPS_LIBCLANG_PATH`.

Toolchain: Rust 1.94.1 (pinned in `rust-toolchain.toml`), NDK r27c at `$HOME/android-ndk-r27c`, JDK 17 at `~/.local/jdk-17`, Gradle 8.7 at `~/.local/gradle-8.7`, Android SDK platform-34.

There is no Kotlin test suite; every Kotlin path is verified by a human looking at a screen — a wiped emulator (the `fips-firstrun` AVD) for first-run and settings-migration paths, a real device (Pixel 9 Pro) for anything involving Wi-Fi, Doze, or the hotspot, which the emulator cannot test. Say which was used when changing Kotlin. Rust tests live as `#[cfg(test)]` modules inside `shim/src/*.rs` (`ble`, `config`, `control`, `dns`, `engine`, `exit`, `exitfind`, `filter`, `forward`, `lib`, `logbuf`, `meshhttp`, `meshout`, `meshtcp`, `packet`, `pump`).

## CI (`.github/workflows/`)

`build.yml` runs on every push to `main` and every PR, and mechanically enforces five constraints this file states in prose — check it before assuming a rule is only advisory:
- **fips pin sync**: the `rev` in `shim/Cargo.toml` and `smoke/Cargo.toml` must match *and* appear in both `Cargo.lock`s (a bumped manifest with a stale lock quietly builds the old fips; the fix is `cargo update -p fips-mesh`).
- **Exit-node fips pin**: `ARG FIPS_REV` in `exit-node/Dockerfile` must be the full commit locked in `shim/Cargo.lock` (GitHub serves no fetch by short hash), so the exit runs the fips the app does.
- **ABI list sync** between `build-native.sh` and the debug `abiFilters` in `android/app/build.gradle.kts`.
- **Page alignment** per ABI, read out of the built `.so` with `llvm-readelf` (0x4000 on arm64/x86_64, 0x1000 on armeabi-v7a).
- **APK contents**: all three `lib/<abi>/libfips_android.so` present in the debug APK, which is uploaded as an artifact.

The `checks` job also runs the host suite as `cargo test --locked`, so a lockfile that drifts from the manifest fails there too, and runs the exit node's `exit-node/test_exitctl.py`. The `android` job is the only place all three ABIs are cross-compiled — it is the meaningful check on a fips pin bump.

There is no automated security scan in CI (the Anthropic security-reviewer workflow was removed in September 2026; reviews are done by hand). `SECURITY-REVIEW.md` is the context for that manual review: the trust boundaries, and the list of deliberate design choices that are *not* findings. CI holds no secrets at all — release signing happens on a workstation — so "Require approval for all external contributors" (Settings → Actions) guards runner minutes, not credentials, and only covers users without write access. The `security-review` GitHub environment and its `CLAUDE_API_KEY` secret outlived the workflow; they are unused and should be deleted from the repo settings, since any job that declares that environment regains the key after a self-approval. `main` requires the `checks` and `android` status checks to pass before a merge (branch protection, since 2026-09-15; not strict, so a PR need not be rebased onto the latest `main` first, and admins can bypass). Before that, several PRs were merged while `android` was still running.

`PR-REVIEW.md` is the maintainers' review checklist — the criteria applied to incoming PRs, several of which exist because the failure already happened once. Read it before reviewing or opening one.

## The fips dependency

`shim/` and `smoke/` depend on fips as a **pinned git dependency**: `fr34aky/fips` @ branch `android-hooks` (rev in both `Cargo.toml`s must stay in sync). The goal is to build against upstream fips with no fork, and the shim uses upstream's own seams wherever one exists: `Node::enable_app_owned_tun()`, `Node::enable_app_owned_udp_fd()`, `Node::enable_app_owned_ble_radio()`, `Node::netmon_trigger()`, the control socket (for commands), and the public `ipv6tun::tcp_mss::clamp_tcp_mss`. Two hooks the fork used to carry are **gone from it** (since the pin 8b8433a, 2026-11-26) because the shim uses those seams instead — do not bring them back: `Node::set_socket_protect()` (and the netmon probe-socket protect) and `Node::control_command_handle()`. What the shim still needs from the fork, with no upstream equivalent yet: public `Node::control_read_handle()` + `ControlReadHandle::query` (upstream has the handle, private; a visibility change, the first thing to propose upstream), `Node::tun_packet_processor()` (the outbound pipeline with its per-destination MSS clamp; upstream tells an embedder to clamp and does not give it the number), the `show_lan_peers` snapshot query (mDNS sightings registry fed by `poll_lan_rendezvous`), `LanRendezvousConfig.exclude_addrs` (keeps tunnel addresses out of mDNS adverts), `UdpConfig.share_port` (two UDP instances of one node on one port: puts SO_REUSEPORT/SO_REUSEADDR on *before* bind for that instance — fips otherwise sets them after bind on purpose, so a second bind of an occupied port fails loudly — and every instance sharing the port must set it), and `UdpConfig.dial_prefixes` (dial-scoped UDP instances: a scoped instance wins outbound selection for remotes inside its CIDR prefixes and is invisible to generic selection and the mDNS advertised-port pick — the FIPS Hotspot seam), family-aware hostname resolution in the UDP transport (`resolve_socket_addr_for`, @ 7836a44, upstream since `e25e8611` so it drops out at the next rebase: a static peer given as a hostname is dialed by transport *type*, so the transport resolves the name itself and used to take the resolver's first answer — on a DNS64/NAT64 carrier that is a synthesized AAAA, unusable from the `0.0.0.0` socket, and every handshake failed with EAFNOSUPPORT/os error 97; it now takes the first answer in its own family and refuses a numeric remote of the other family with a message naming both), `NostrRendezvousConfig.open_discovery_max_peers` (@ 6c95f54 + 3a747ec: ceiling on the peers this node dials from adverts, in total — queued + connecting + connected; inbound links are not counted; 0 = no ceiling of its own. The reconciler remembers which peers came from the overlay and prunes that set to the live ones on EVERY sweep, knob or not — the first cut pruned only under the knob and grew forever on every existing `policy: open` server, caught by two independent reviews — and dials the freshest advert first, since the cache is up to an hour old and both device runs filled a cap of 3 with entries that no longer answered — the Settings "Discover peers via Nostr" seam), and `Node::nostr_rendezvous_arc()` + `NostrRendezvous::relay_status()` (a `Vec<RelayStatusView {url, status, connected}>` off nostr-sdk's relay pool — fips fixes that pool at node start and reports nothing about it, so this is how the Overview shows which relays are actually connected). mDNS is compiled in unconditionally and gated at runtime by `node.rendezvous.lan.enabled` (shim knob `enable_lan_mdns`, default off in the shim but default ON from the app since 0.3; the Kotlin side pairs it with a `MulticastLock` held only on Wi-Fi, or while a FIPS Hotspot is joined. Discovery over the phone's OWN tethering hotspot works without the lock — device-verified on 0.6.0, underlay cellular, a laptop running fips on the hotspot was discovered and linked — so do not extend the lock to tethering. That is also the only way a tethered device gets the mesh: tethered traffic is kernel-forwarded with no UID, netd's VPN rule matches `iif lo uidrange` only, and tethering never picks a VPN as upstream, so it cannot be captured by the `VpnService` or listed as a mesh app — the hotspot overlay forces LAN mDNS on).

The local `fips/` directory is a **git worktree of `~/fips` on `android-hooks`**, ignored by this repo — it is NOT what builds use. To develop against it, add to `shim/Cargo.toml` (and `smoke/Cargo.toml`):

```toml
[patch."https://github.com/fr34aky/fips"]
fips-mesh = { path = "../fips" }
```

The patch key is the **package** name: upstream publishes the crate as `fips-mesh` (its library is still `fips`, so code says `fips::…`), and both manifests depend on it as `fips = { git = …, rev = …, package = "fips-mesh" }`. A `fips = { path = … }` patch matches nothing, and cargo only warns that it went unused while the build quietly uses the git pin.

On 2026-10-23 `android-hooks` was rebased onto upstream master (the 0.6 line: 535 upstream commits, crate renamed `fips-mesh`, `fips::upper` split into `fips::ipv6tun` / `fips::hosts`) and force-pushed; the pre-rebase tip `f4a811e` is tagged `android-hooks-pre-0.6` (and the one before it `android-hooks-pre-netmon`), so lockfiles of earlier releases stay fetchable — tag the old tip the same way before any future force-push. On 2026-11-26 the branch was rewritten on the same upstream base without those two hooks (13 commits → 12: the netmon probe-protect commit `dad00048` dropped whole; the socket-protect half cut out of the first commit `aba0181c`, whose `TunPacketProcessor` half remains as a commit of its own; the `ControlCommandHandle` half cut out of `21a4e524`, whose `show_lan_peers` half remains; the rest unchanged in content. The fork's test of `tun_packet_processor()` on a started node went with the protect test it shared a function with — here `exit::tests` and the smoke run drive a packet through a started node's processor); the tip before that, `a4f4816`, is tagged `android-hooks-pre-slim`. The fork's own NetmonTrigger and 32-bit `msg_namelen` commits were dropped as upstream carries both.

When bumping the pin: change the `rev` in both `Cargo.toml`s and update both `Cargo.lock`s. `smoke/Cargo.lock` deliberately pins `rustables` 0.8.7 (known-good against the host libclang).

## Architecture

Everything crosses the JNI boundary as JSON strings — hand-written JNI (`jni_api.rs`, twenty-five `Java_org_fips_android_FipsNative_*` exports: start/stop/status/isRunning, deriveIdentity, dnsServer, onNetworkChanged, networkHint, namesOnline, query, connectPeer, resolveNpub, recentLogs, meshHttpGet, findExits, exitProbe, and the nine `ble…` ones of the Bluetooth radio seam), no UniFFI. `FipsNative.kt` is the Kotlin `external fun` mirror. Panics are caught at the boundary.

Data path (the core seam): Kotlin's `VpnService` establishes the TUN (addresses = the node's fips /128 + an IPv4 source for clearnet — the node's exit-node inner address, `inner_ipv4` from `deriveIdentity`, routes `fd00::/8` + `0.0.0.0/0`, plus `::/0` only while the underlying network has IPv6 internet — advertising it unconditionally black-holes IPv6 because the forwarder's userspace stack SYN-ACKs before dialing, defeating Happy Eyeballs; without `::/0`, two host routes keep AAAA queries — and thus AAAA-only `.fips` names — resolving: `2000::/128` satisfies netd's AI_ADDRCONFIG probe (UDP connect to `2000::`) and `2001:4860:4860::8888/128` satisfies Chromium/WebView's own IPv6-reachability probe (UDP connect to Google DNS, cached 60 s — without it `.fips` browsing dies exactly one minute after landing on a v4-only underlay); MTU 1280) and hands the fd to the shim, which dups it. When the IPv6 decision flips (network switch or link-properties change), the service re-establishes the tunnel and passes the NEW fd to `onNetworkChanged`; every rebind also passes a freshly regenerated config JSON so per-network state (the hotspot transport) rides the same path. A plain underlying-network switch that leaves the IPv6 decision alone does **not** restart the node (since the netmon pin, fips `android-hooks` @ bf6f442; the trigger, `Node::netmon_trigger()`, is upstream fips API since #146): the node's protected wildcard sockets route per packet over the new default network, and fips's `node.netmon.*` detector heartbeats the peers whose path moved (on by default; its netlink wake is refused to apps by SELinux, so the service pokes it through `FipsNative.networkHint()` → `Node::netmon_trigger()` the moment the callback fires, with the 5 s poll as backstop) so the far side re-pins within one RTT — sessions and routes survive. Only an IPv6-route flip, a FIPS Hotspot join/leave, and a changed mesh-app selection still rebind, and of those only the hotspot transition restarts the node. The other two need a new *tunnel* — routes and `addAllowedApplication` are fixed at `establish()` — but not a new node, which never sees the fd (it exchanges packets with the pump): `rebindOnce` hands over the new fd with the same config, and `network_changed` moves the pump's reader and writer onto it (`Pump::swap_fd`) while the node, its links and sessions, the bridge, the forwarder and the DNS proxy keep running. Before, every such flip was a full node restart, ~6 s of no mesh on a Wi-Fi↔LTE switch. A changed config (the hotspot overlay) or a swap that cannot stop the old reader/writer in 2 s still restarts the node. The service records the app set each tunnel was built with (`tunnelMeshApps`), `rebindOnce` replaces the tunnel whenever the stored selection differs, and the pickers nudge it through `FipsVpnService.requestRebind()` (`ACTION_CONFIG_CHANGED`) once per visit — from `onPause`, skipped on a rotation, and not per toggle. A nudge that arrives while the first connect is still establishing is deferred until the engine is up rather than raced against it. Network callbacks are coalesced, never dropped: a hand-over emits a burst of them over seconds while a rebind (full node restart) takes seconds itself, so requests queue on a flag served by a single worker that re-checks after every pass — the burst always ends with a rebind against final network state. Validated networks are preferred over unvalidated ones (a dying Wi-Fi keeps its transport for 10–30 s; follow the OS default to cellular instead). `pump.rs` runs reader/writer/bridge threads over the dup'd fd; each outbound packet goes through DNS intercept, then a mesh/clearnet classifier: `fd00::/8` goes through the node's own `TunPacketProcessor` (forward with MSS clamp / hairpin / ICMPv6 respond / drop — byte-identical to the daemon's system-TUN path), everything else to the userspace forwarder. The processor's clamp is per destination — the path MTU the node has learned, which on a Bluetooth link is routinely below the IPv6 minimum, where no Packet Too Big brings a phone's TCP down to it — and that map is the node's: a constant in the shim was tried for a day (2026-11-26) and was a regression for exactly those paths. The processor covers outbound only; the bridge clamps the MSS of an inbound SYN or SYN-ACK to 1143, the segment of a 1280-byte path (`meshout.rs`, ahead of the divert, so the shim's own smoltcp flows are held to it too), as an upper bound. The mesh→app direction passes the stateful inbound firewall (`filter.rs`, shim knobs `inbound_filter` default-on + `inbound_ports`): new inbound flows are default-denied unless the port is allowlisted, replies to outbound-initiated flows (4-tuple flow table fed by the reader) and ICMPv6 always pass, and non-TCP/UDP/ICMPv6 next-headers are dropped unparsed.

- `engine.rs` — singleton node lifecycle on a dedicated current-thread tokio runtime: in-memory `fips::Config` → `Node::new` → `enable_app_owned_tun` → `enable_app_owned_udp_fd` → `start`. Status and every `show_*` query are served lock-free from `ControlReadHandle` snapshots, in process — Kotlin polls them on its **main thread** (Overview every 2 s, Diagnostics five queries per 2 s, `FipsBle` every 30 s), so they must stay reads from memory. They were moved onto the node's control socket for a day (2026-11-26) to drop that fork hook, and three code reviews in a row found new ways a socket round trip could hold the UI thread or show stale figures; do not repeat it — get upstream to make the handle public instead. Only the `connect` command goes over the **control socket** (`control.rs`; shim knob `control_path`, which `ConfigStore` sets to `files/control.sock` — app-private, so no other UID can reach it; unset, the engine picks a file in the system's temporary directory, which only works on the host), because a command has to reach the rx loop: one blocking connection with a single 10 s deadline over connect, write and read (2 s of grace for a socket not bound yet plus the 5 s fips gives the rx-loop round trip, with room, so fips's own timeout answer arrives) (the connect through `SO_SNDTIMEO`, since `UnixStream::connect` has none), called off the main thread, retried for 2 s while the socket is not there yet (the node binds it on a task of its own after `start` returns). The `relays` array in `status_json` comes from a task on the node runtime (the relay pool can only be awaited there) that refreshes a shared slot once per `status_json` call (a `Notify` permit, so a backgrounded app costs no wakeups). `network_changed` with an unchanged config swaps the pump onto the new tunnel fd and keeps the node; with a changed config (the hotspot overlay) it restarts the node on the given fd (fips has no runtime socket-rebind API, and the overlay is a second transport).
- `dns.rs` — mesh names: a `.fips` query whose label is in the app's hosts file (shim knob `hosts_path`; fips's own `name npub` format, read through fips's `HostMapReloader`, re-read on an mtime change with one stat per `.fips` query — so an edit needs **no rebind**) is re-asked as `<npub>.fips` and the reply re-issued under the asked name (`npub_query` / `answer_as_asked`). fips has this feature itself but only for the hardcoded `/etc/fips/hosts`, which an app cannot write; the responder still has to see the npub query because answering is what registers the identity with the node, so the shim must not answer from the map alone. Names are single labels (fips's `validate_hostname`): `www.home.fips` does not resolve. Otherwise: covered-app DNS is sent to the `fd00::53` sentinel (`engine::DNS_SENTINEL`, exposed as `FipsNative.dnsServer()`), NOT the node's own tun /128 — the kernel would deliver packets addressed to the interface's own address locally, so they'd never reach the TUN fd. The pump intercepts port 53 to that sentinel: `.fips` names → in-process responder at `[::1]:5354`; everything else → configured upstreams over protected sockets; SERVFAIL on total failure.
- `forward.rs` — userspace clearnet forwarder (`ipstack`-based tun2socks; TCP/UDP, not ICMP) dialing protected sockets per flow, so covered apps keep normal internet.
- Socket protection: the shim's hook (`crate::SocketProtect`) crosses JNI (JavaVM + GlobalRef, callable from any thread) to `FipsVpnService.protectFd`, which calls `VpnService.protect()` and moves the FIPS Hotspot socket onto its network. It gets every socket the shim dials itself (forwarder, DNS upstreams) and each UDP **listen** socket of the node — those through upstream's `enable_app_owned_udp_fd`, drained right after `node.start()` returns and before the rx loop, on the node thread and nowhere later: the fd is a borrow valid while the transport runs, and fips sends one again only when a stopped node is restarted, which the engine never does (`engine::tests::hotspot_overlay_starts_both_transports` checks both instances' fds arrive, the hotspot one bound to its address). Not covered (no fd access): fips's TCP transport, netmon probe and STUN sockets, the UDP sockets of Nostr NAT traversal (a hole-punched link runs over an adopted socket the seam does not announce), nostr-sdk relay websockets, mDNS — benign because the fips app itself is never captured by its tunnel with a default route (outside it when mesh apps are selected, `fd00::/8` only otherwise). That is an invariant now, not a convenience: capturing the app's own UID with `0.0.0.0/0` would send the node's underlay into its own tunnel (`AppPickerActivity.storedMeshApps` is the one place the stored list is read and never returns this app, and `establishTunnel` skips it again).
- `config.rs` — `ShimConfig` JSON → validated `fips::Config` (knobs incl. `worker_threads`, `battery_saver`, and `fips_yaml` — a raw fips.yaml base config parsed by fips's serde); `derive_identity` produces the nsec/npub/fd-address triple. Identity is generated in Rust and persisted via Android Keystore (`SecureStore.kt`/`IdentityStore.kt`). `fips_yaml` (a raw fips.yaml that becomes the base config and supersedes the structured settings, with the hotspot overlay then ignored) is still supported by the shim but **no longer reachable from the app** — the Settings section was removed in the 0.3 UI overhaul and `ConfigStore.RETIRED_KEYS` deletes any stored value on first run, because a stale one would keep overriding everything with no UI left to clear it.
- `logbuf.rs` / `lib.rs::init_logging` — 1000-line ring buffer behind the `tracing` writer (fanned out to logcat), drained by `recentLogs` for the in-app log viewer. The subscriber installs once per process but the level filter sits behind a reload handle, so a log-level change takes effect on the next connect (every engine start re-calls `init_logging`) without killing the app process. At error, warn and info the log is kept to what a reader can act on (`lib.rs::log_directives`, `logbuf::Quiet`): `ipstack` and fips's netmon are capped at error (a warning per idle-closed connection; one at every start for netlink events SELinux always refuses), two nostr-sdk lines that only restate the line before them are dropped, and the same message within 2 s is shown once — Android aborts every relay connection when the Wi-Fi roams and nostr-sdk reports each two to four times. Debug and trace show everything, so use those when a line seems to be missing. At every level the access token in a mesh relay's loopback URL (`ws://127.0.0.1:<port>/<token>`, which nostr-sdk logs) is replaced by `<token>` before the line reaches the buffer or logcat.
- `packet.rs` — IPv6/UDP build+parse for the DNS proxy (the UDP checksum is mandatory over IPv6).
- `names.rs` / `meshudp.rs` — public domain names over fips (`www.example.org` → a mesh node), the phone half of `fr34aky/fips-pub-domains` (spec and docs live there: `docs/spec.md`, `docs/android.md`; the crates `pubdom-core` (policy, no I/O) and `pubdom-resolve` (relays, legacy TXT verification, pin file) are pinned git deps in `shim/Cargo.toml` like fips; the repo is public). The DNS proxy asks `Names::lookup` for every non-`.fips` name before the upstreams: pins first; online the `_fips-dns.<domain>` TXT record from the configured upstreams (DNSSEC-validated when the zone is signed; while a validated Internet network exists, a domain with no pin is asked plainly first and validated only when a record exists — `names.rs` `PhoneTxt`, fips-pub-domains 0.2.4; without one the plain probe is skipped, because a router with no uplink or a captive portal answering "no record" would end the lookup before the mesh-only path), a claim from the relays only after a TXT hit, then step 3 — a DNS query to the domain's server over the mesh, sent from the node's own address through a smoltcp **UDP** socket (`meshudp.rs`, the UDP twin of `meshhttp.rs`; `Divert` now keys UDP flows too), answered `CNAME <npub>.fips.`; when that names a node other than the server just answered, an ICMPv6 echo through the same stack must come back within 1.5 s (fips drops traffic for unknown nodes silently, so nothing else tells a real node from a bogus zone entry) — and the reply the app gets carries that node's `fd…` AAAA with the public addresses suppressed. Offline, a domain with no pin and no DNSSEC proof in its claim resolves once `names_attestation_threshold` of the `names_witnesses` (Settings; npubs, validated by `ConfigStore.witnesses`) have attested its server — attestations are fetched by those authors only and from the mesh relays only, so the witness list never reaches a public relay. *Trust my Mesh names as witnesses* (`names_witnesses_from_hosts`, off by default) adds the hosts file's nodes — the sync upstream first, then each name's node, `ConfigStore.hostWitnesses` — to the typed list, capped at 32 in total. `FipsNative.namesOnline(validated)` is sent at start (the OS default network's answer until the callback reports) and whenever any non-hotspot network's `NET_CAPABILITY_VALIDATED` flips (`FipsVpnService.pushNamesOnline`); the shim remembers it across rebinds (`engine::INTERNET_VALIDATED`). Without validation the TXT lookup gets a 500 ms wait instead of 1.5 s, so a first offline lookup fails into the mesh-only path within the budget; it is shortened, not skipped — a Wi-Fi that works but never passed Android's probe still verifies online, and the resolver keeps believing it is online so no public relay is asked without a TXT hit. INTERNET alone is not the signal: a router that blocks the phone leaves it set. `names_dnssec` (Settings, on by default, always sent) is the resolver's `dnssec`: off, the record is taken from plain DNS answers (a single resolver's is enough, pinned as `dns-single`) and no DNSSEC proof in a claim is accepted, so an offline domain never seen resolves through witnesses alone — the way to exercise the witness path on a phone, together with Settings' **Forget verified domains** (deletes `names-pins.json`; applies on the next connect), since a pin made online would otherwise answer first. For a name under no pinned domain, and only with a validated Internet, the proxy fetches the legacy answer on a second thread while the lookup runs — started by the lookup itself through the `pending` callback of `Lookup::lookup`, once one poll of the resolver found it not settling at once (a cached decision or a record type never over fips settles there, with no thread), and the lookup returns `Early` as soon as one upstream has denied the record for every candidate domain (the library's `denied_by_an_upstream`; only with the plain probe, so only with a validated Internet): the legacy answer then goes out without waiting for the other upstreams — unchanged if the decision is in by the time it arrives, capped at 5 s if not, and replaced by the answer over fips if that comes first. `Legacy` from it is "not over fips" and the query goes upstream unchanged, `Capped(n)` goes upstream with the answer's TTLs capped at *n* seconds so the resolver asks again soon — 5 s when the lookup overran its 3.5 s budget and is still deciding, or the time to the resolver's next attempt when the domain is over fips but no server or target node is reachable now, as on the first lookup after connecting before the mesh session to the server is up (`pubdom_core::unavailable_ttl`, floored at 5 s): during a server's first backoff window (20 s) the resolver asks it again in the background every 3 s and ends the window when it answers (fips-pub-domains 0.2.10), so the cap is ~5 s there; later windows grow to 3 h for a server that stays down. To make that first lookup rarer, `Names` warms the path to every pinned server (`Resolver::warm`: register the identity, one echo; up to 16) 3 s and 10 s after the resolver starts — a connect or a node restart, not a network switch, which the node and its sessions survive — since on a Pixel 9 Pro discovery of a server three hops away took 14 s after a connect: a name never becomes unreachable because of this code, and a claim alone never resolves — except offline, when its DNSSEC proof verifies against the root key (spec §5.5; needs a mesh relay, configured below). Shim knobs `names_pins_path` (set = on; the app-private `names-pins.json`, same schema as the desktop daemon's), `names_mesh_relays`, `names_allow_unverified_offline`; Settings → "Public domain names over fips" (`public_names`, `DEF_PUBLIC_NAMES` = true) decides whether the path is sent, and the "Mesh relays for public names" field below it (`names_mesh_relays`, `ws://<npub>.fips[:port]` per line, validated by `ConfigStore.normalizeMeshRelay`) lists relays on fips nodes. nostr-sdk's sockets cannot reach `fd00::/8` from this app, so `meshtcp.rs` gives each mesh relay a loopback listener and carries every accepted connection over the in-process smoltcp TCP stack (same device and `Divert` path as `meshhttp.rs`); the resolver is handed `ws://127.0.0.1:<port>/<token>`. Loopback is shared by every app and the connection leaves from this node's address, so the listener admits only the holder of that random path token (checked and stripped from the upgrade request before anything touches the mesh), at most 4 connections per relay. The pipe blocks on one event channel (mesh packets and local reads) with bounded buffers both ways (the local reader pauses at 256 KiB; local writes time out after 200 ms so the stack keeps running), and the listener blocks in `accept` until `Drop` wakes it — an idle relay connection costs a wakeup every 30 s plus smoltcp's keep-alive. With a mesh relay configured, an offline phone can verify a domain it never saw from the DNSSEC proof in its claim. Not yet on the phone: the TCP fallback for a truncated step 3 answer (a CNAME never is)
- Exit probe (`engine::exit_probe_json`, `FipsNative.exitProbe`, `meshudp::ping_sized`): while the Overview is on screen and an exit is in use, `OverviewFragment.probeExit` asks every 30 s whether the exit answers a small ICMPv6 echo and a **full-size** one (1280 bytes on the mesh, `meshudp::FULL_PAYLOAD`), and the Internet route card says so. It exists for one state nothing else showed: the exit answers and its DNS answers, the card says "through exit node", and no page loads, because the mesh route between phone and exit loses packets near 1280 bytes — a hop that carries less (a transport MTU of 1280 leaves 1203 for IPv6) and a node on the way too old to split for it. Device-observed 2026-11-25 on the Pixel 9 Pro against a `fips-exit` node on fips `67c4c60e62`: echoes up to 1198 bytes arrived, none from 1228, and it came and went with the mesh route (a tree parent switch); upgrading fips on the exit and its peer fixed it. The reply must be as long as the request, so one cut short does not count. Only from the status poll, so nothing runs in the background. Both exit kinds answer echo (the container's `mesh_in`, fips's own firewall baseline). No result (not connected, the exit changed under the probe) shows nothing rather than a guess.
- `exitfind.rs` — finding exit nodes (Internet route → **Find exit nodes** → Search; `FipsNative.findExits`). An exit that wants to be found publishes one Nostr event signed with its own fips key (`exit-node/advert.py`, which specifies the format: kind 30078, `d` = `fips-exit`, `v` = `1`, `access` = `open` | `allow-list`, optional `name`/`about`, a NIP-40 `expiration`; the container's `ADVERTISE=1`, and `OPEN=1` is what makes an exit usable by an npub its operator never listed). A fips identity is a Nostr key, so the advert's author IS the exit: the npub handed to the app is the one the node routes to, and that is all an advert proves — name and note are the operator's words and "open" is a claim. The search asks the mesh relays from Settings (`names_mesh_relays`, each through its own `MeshRelayProxy` for the length of one search — the path that works with no internet) and, only while `engine::INTERNET_VALIDATED`, the public relays (the user's list, else pubdom-resolve's defaults). **Only from the button, never on a timer**: the query tells a public relay that this address is looking for an exit. Events are streamed and each is reduced at once to an advert's six known tags, the first of each, cut to 1024 bytes (`raw_of`, which also verifies the signature), and reading stops at 2000 events: the library bounds a message's size, not how many a relay sends, so without this a relay decided how much the phone held. `advert_of` drops anything odd (wrong kind or marker, another contract version, an unknown access word, no or a past expiration, one more than 31 days ahead, a date more than 10 minutes in the future); `tidy` reduces operator text to one printable line with no control or bidi-formatting characters (40 / 200 characters); `select` keeps one advert per exit, never this node's own, open ones first, at most 100. Nothing found is used by itself: the app lists it, Add puts it in the exit list, and selecting stays a separate tap. `nostr-sdk` became a direct dependency for this, at the version already in the lockfile. `fetch` is not in the host suite (it needs a relay): `exitfind::tests::reads_adverts_from_a_relay` is `#[ignore]`d and run by hand against `nak serve` holding adverts made by `advert.py`.
- `ble.rs` — Bluetooth (BLE) as a fips transport with the radio in the app (Settings → **Bluetooth**, `ble_enabled`, `DEF_BLE` = false; Android 10+ for L2CAP channels, the switch is disabled elsewhere; device-verified on a Pixel 9 Pro against a Linux fips node on BlueZ, with the phone as the dialing side only — a peer dialing the phone at the PSM in its advert, two phones, Android 10/11 and the battery cost are unmeasured). fips has a BLE transport (advert with the FIPS service UUID, L2CAP channels) but cannot open a radio on Android, where scanning, advertising and the sockets are Java APIs; it drives one the embedder supplies (`fips::transport::ble::io_radio`: a seven-method command trait, and a bridge the embedder feeds adverts, connections and bytes). Shim knob `ble` adds one `transports.ble` instance (`auto_connect` on, `max_connections` = `config::BLE_MAX_CONNECTIONS` = 3 instead of fips's 7 — every held link costs keep-alives) and the engine arms the node's radio slot (`Node::enable_app_owned_ble_radio`, before `start`). `ble::GLOBAL` holds the radio the app installed (`FipsNative.bleInstall(radio)`, a `FipsNative.BleRadio`) and the running node's slot and joins them whenever both exist, in either order: Bluetooth turned on after the mesh is up, or a node restart under a running radio, restarts neither. Each joining is a fresh fips bridge that numbers channels from 1, so every id that crosses to Kotlin carries the bridge's generation (`ble::tag`) and an id from an earlier bridge reads as "channel gone" — what makes the app's reader and writer threads close their sockets — instead of hitting the new bridge's channel of the same number. Bytes: Kotlin pushes reads with `bleRecv` (blocking, one reader thread per channel — a dropped chunk would desynchronise fips's framing) and pulls writes with `bleNextSend`. **Battery policy is the Kotlin radio's, by design**: fips asks for scanning for as long as the transport runs and probes (connects to) every advert it is shown, so `bleStartScanning` only means scanning is wanted, and an advert not reported is a link never made. fips compiles the bridge and the slot on Android only (`cfg(target_os = "android")` in fips), so `ble::android` is not built or tested on the host: the host tests cover the join/generation logic against a mock bridge, and the `android` CI job is the only check that the fips-facing half compiles. On a non-Android build the engine drops `transports.ble`, or fips would open the machine's own adapter. The Kotlin radio is `FipsBle.kt`: one instance per radio session, made by `FipsVpnService.syncBle()` when the setting is on, the permissions are granted (`BLUETOOTH_SCAN` with `neverForLocation`, `BLUETOOTH_ADVERTISE`, `BLUETOOTH_CONNECT` on Android 12+, asked when the switch is turned on; fine location before that) and the adapter is on, and shut down when any of those stops holding (a receiver on `BluetoothAdapter.ACTION_STATE_CHANGED`; `rebindOnce` re-checks). `ConfigStore` sends `ble` whenever the setting is on and the phone supports it, permissions or not — the transport runs without a radio — so toggling the setting needs a reconnect, while switching Bluetooth on does not (a permission granted later is noticed at the next rebind or Bluetooth toggle). Its scan policy: scan only while `status.link_count` is 0 or the app is on screen (`FipsBle.setForeground`, from `MainActivity.onStart/onStop`), re-decided every 30 s on a main-looper timer (uptime-based, so it does not run in sleep — a running scan continues through sleep, a stopped one is reconsidered at the next wake; it reads the link count with `query("show_status")`, not `status()`, which would wake the relay-status refresh), and a scan that has run 20 minutes is restarted, because Android silently downgrades one to "opportunistic" at 30; the scan is `SCAN_MODE_LOW_POWER` with a `ScanFilter` on the FIPS service UUID, and each address is passed to fips at most every 10 s. Advertising is `ADVERTISE_MODE_LOW_POWER`, connectable, the 27-byte advert fips specifies (service UUID `9c90b790-…`, PSM as service data under `0x9C90`), for as long as the radio is up. Each channel has a reader and a writer thread that both block (the writer in `bleNextSend`, 10 s), so an idle link costs no wake-ups of its own. A dial uses the `BluetoothDevice` the scanner handed over (kept by address, 64 entries): `getRemoteDevice` would treat a random address as a public one.
- `exit.rs` — exit nodes: shim knob `exit_node` (an npub; absent = the phone's own connection), sent from `ConfigStore.selectedExit` (`exit_nodes` = JSON `[{name, npub}]`, at most `MAX_EXITS` = 16, and `exit_selected`; edited in `ExitsActivity`, Overview's "Internet route" card, which like the relay editor nudges one `requestRebind()` on leaving). The pump sends a covered app's IPv4 internet packet, MSS-clamped to 1200 both ways (`exit::MSS_IPV4`, a 1280-byte mesh packet once wrapped; the exit's forward chain clamps the same), wrapped in IPv6 next header 4 from the node's address to the exit's (Linux `ip6tnl` mode `ipip6`, `encaplimit none` — no extension headers), with the inner source `inner_ipv4` = `100.64.0.0/10` | the low 22 bits of fips-address bytes 1..4. It is also the tunnel's IPv4 address, so nothing is rewritten and ICMP errors reach the app's socket. Replies are written to the TUN ahead of `filter.rs` but only through `ExitSwitch`'s own flow table (`filter::FlowTable`, cleared on an exit switch): replies to flows an app opened, ICMP errors only quoting one, no allowlist or off switch, and any other IPv4-in-IPv6 is dropped — the exit's operator must not be able to reach a listening app. That formula is the contract with `exit-node/exitctl.py` (`test_exitctl.py` checks vectors printed by `exit::tests::print_vector`); never change it. IPv6 internet traffic gets ICMPv6 administratively-prohibited, and `FipsVpnService.wantIpv6Route` claims `::/0` whenever an exit is selected so none leaves around it. An unreachable exit blocks; there is no fallback to the forwarder. DNS: every non-`.fips` query goes to port 53 on the exit's fips address over `meshudp` and nowhere else (no upstream fallback; SERVFAIL re-registers the exit's identity), and the names resolver is set offline (`Names::set_exit_selected` → `Resolver::set_online(false)`) and handed only names under a pinned domain (`Lookup::pinned`), which it answers from the pin with no TXT query and no relay; an unpinned name never reaches it (offline it would ask the public relays) and goes to the exit's resolver. `engine::select_exit` orders the two so no pinned query is looked up online with an exit selected. Pins are not refreshed meanwhile. The shim compares configs without `exit_node`, so changing the exit switches the running node's `ExitSwitch` with no restart. The server side is `exit-node/`: a Docker container whose `README.md` is the operator guide and the full contract. Its allow-list is `data/allowed_npubs`, bind-mounted read-only, and its identity is in the named volume `state`, because with `cap_drop: ALL` the container's root cannot write a host directory owned by the operator. `PUBLISH` (`MESH_PORT=IPv4:PORT`) lets every allowed npub reach a LAN or host service through the exit, with or without the exit selected: a `socat` TCP relay per entry on the exit's fips address, plus a `published_tcp` port set in the mesh-side firewall — a relay because clients arrive over IPv6 and the kernel's NAT cannot DNAT to IPv4, which also leaves the forward chain's private-range block untouched (never loosen that to reach the LAN). The network's own public IPv4 is blocked too (`blocked_dyn`): from inside it is the router, whose admin page and NAT loopback reach the LAN. The entrypoint looks it up over HTTPS (`PUBLIC_IP_LOOKUP`, every valid answer blocked, so a lying source only adds a block), refuses to start without an answer, and re-checks every `PUBLIC_IP_INTERVAL` s, swapping the set atomically. `e2e-test.sh` runs it from `compose.yaml` itself, not a copy of its flags; run it after changing either. CI runs only `test_exitctl.py` and checks the Dockerfile's `FIPS_REV` against `shim/Cargo.lock`, so a fips pin bump must bump it too.
- `meshhttp.rs` — in-process HTTP GET to a mesh node (`FipsNative.meshHttpGet`, used by the Mesh names sync). The app's own UID is outside its tunnel whenever mesh apps are selected (and must stay out — see the no-selection note below), and a VPN network refuses `bindSocket` from a UID it does not cover, so a Kotlin socket cannot reach `fd00::/8`. Instead a smoltcp TCP client speaks from the node's own address: its packets go through the node's `TunPacketProcessor` + outbound channel exactly like an app's, and the pump's bridge hands replies (and ICMPv6 errors quoting them) back through `Divert` — keyed on (remote addr, remote port, local port), local ports 61000–65535 above the kernel's ephemeral range — before the inbound firewall and the TUN. It first asks the local `.fips` responder for `<npub>.fips`, since that is what registers the destination identity with the node (without it the node answers the SYN with destination-unreachable).

The shim crate is both `cdylib` (the .so Kotlin loads) and `lib` (so host tests can exercise everything except the JNI surface itself).

Kotlin side: `FipsApplication` applies the colour scheme before any activity exists (`ConfigStore.applyTheme`: Settings → Appearance, `theme` = `dark` (default) / `light` / `system`, via `AppCompatDelegate`; the Material 3 DayNight theme in `themes.xml` does the rest, so no view knows which it is). `MainActivity` hosts bottom-nav fragments (Overview / Settings / Diagnostics), `FipsVpnService` owns the tunnel + foreground notification + network-change handling (ConnectivityManager callback → `setUnderlyingNetworks` + `onNetworkChanged`), `OverviewFragment` shows the identity, the "Nostr relays" card (`status.relays`, each public relay with its live connection state), and owns backup/restore (reveal the nsec + clipboard copy flagged `EXTRA_IS_SENSITIVE`; restore validates a pasted key through `deriveIdentity` and stores the bech32 form it echoes back — never pass that function an empty string, which means "generate" and would silently mint a new identity). Restore and regenerate are blocked while `FipsNative.isRunning()`. `HostsActivity` (Overview's "Mesh names" card) edits the name → npub address book; `HostsStore` owns it, and the file `files/hosts` IS the store — no prefs copy — written via temp + rename because the shim may read it at any moment, with `nameError` mirroring fips's `validate_hostname` (a name fips rejects would be listed in the app and never resolve) and npubs validated through `FipsNative.resolveNpub`. `buildConfigJson` always sends `hosts_path`, file or no file, so the first name added while connected works. Optionally the same screen pulls names from a node running fips-ui (`HostsSync`, off by default): `GET /api/hosts` on the upstream's fips0 address over `meshHttpGet`, hourly by default (fips-ui's own default is 5 min — too much wake-up for a phone) and on Sync now, only while connected; a connect resumes the schedule rather than pulling. The names go into fips-ui's marked block (`# >>> fips-ui sync from <npub>` … `# <<< fips-ui sync`) at the END of the hosts file, so a synced name wins over a local one; `HostsStore.load`/`save` see only the lines outside it, `loadSynced`/`saveSynced` only the block. Semantics follow fips-ui `server/hosts-sync.ts`: validated entries, ≤ 2000, an answer carrying `error` never taken as "no names", unreachable/403 backs off to daily, turning sync off removes the block. fips-ui's guard drops TCP from npubs not on its allow-list in the kernel, so a missing viewer entry shows as a timeout, not a 403. Diagnostics' probe field takes a mesh name too. `AppPickerActivity` selects the captured apps (with no selection — or when every selected app has been uninstalled — the tunnel allows only the fips app itself **and claims only `fd00::/8`: no default route, no DNS server**. Capturing ourselves with the full routes was never the no-op it was taken for: the app's own DNS lookups and relay sockets went into the tunnel, and during node start nothing serves it yet — the pump, its DNS proxy and the forwarder only come up once `start` returns — so the bootstrap peer's hostname sat in the resolver's ~10 s timeout, the first handshake failed, and a fresh install took up to ~25 s to its first link. Selecting an app rebuilds the tunnel with the full routes), `ConfigStore` holds the settings, renders them into the shim's config JSON, and owns their defaults as `DEF_*` constants — read those via `ConfigStore.lanMdns()`/`hotspotEnabled()`/`DEF_*` rather than repeating a literal at a `getBoolean` call site, or the service and the UI drift apart. The Diagnostics tab is `TroubleshootFragment.kt` (the class name does not match the tab label); `Updater.kt`/`UpdateUi.kt` implement the in-app updater. FIPS Hotspot (Settings toggle, API 29+, needs the fine-location runtime permission — Android hides SSIDs/scan results without it): while connected, the service auto-joins the open SSID `!FIPS` via two paths — a `WifiNetworkSuggestion` (API 31+; platform-managed city-scale auto-join/roaming whenever the primary Wi-Fi slot is free, spotted by a location-flagged Wi-Fi callback; the service declares the `location` FGS type for this) and a `WifiNetworkSpecifier` local-only secondary request for the dual-Wi-Fi case, filed ONLY when a scan shows `!FIPS` in range (a periodic scan kick runs while armed and unjoined; the system barely scans on its own) with the strongest beacon's BSSID pinned (SSID-only requests re-prompt even for approved APs — observed on Android 17; approval is stored per BSSID, so pinned = silent rejoin, and a specifier session is one-shot: on loss it is torn down and re-filed on the next sighting). Neither join is an underlay candidate (`preferredUnderlying` excludes the hotspot network); on join the service rebinds the node with `hotspot: {addr, prefix_len}`, which the shim turns into a second UDP transport bound to that address on the main instance's port (both instances carry `share_port`, or the second bind fails with EADDRINUSE and the node starts DEGRADED on one transport — this shipped broken from 0.4.0 until the `share_port` pin, because upstream moved the reuse flags after bind and the only test checked the config's shape, not that two sockets actually bound; `engine::tests::hotspot_overlay_starts_both_transports` now does. Unicast delivery prefers the most-specific socket, so the single mDNS-advertised port serves every interface) with `dial_prefixes` = the link subnet, and `protectFd` moves the matching socket onto the hotspot `Network` via `bindSocket` (wildcard/protected sockets otherwise route via the default network only).

UI conventions (the 2026-09 refresh): one theme, `Theme.Fips`, maps the **full** Material 3 role set onto `fips_*` colours, and every one of those has a `values-night/colors.xml` twin (navy surfaces from the launcher icon) — a colour added to one file needs the other, and a `colorPrimary`-only theme is what made dark mode unreadable before. Layouts use the shared `Widget.Fips.*` styles (`Card`, `Summary`, `Label`, `Mono`, …) instead of per-view radius/colour attributes. The project builds with `android.nonTransitiveRClass=true`, so Kotlin cannot resolve Material's `R.attr.*`: state-dependent colours are XML state lists (`res/color/power_bg.xml`: activated = connected, selected = starting) and Kotlin only flips view states. Overview's connection card is a **single toggle**, not a Connect/Disconnect pair, and its meaning is derived from three signals — `FipsNative.status().running`, `FipsVpnService.tunnelActive` (true from `ACTION_CONNECT` to `shutdown()`, so it stays true across a rebind while the engine reports not-running for ~2 s) and `MainActivity.isConnecting()` (a 3 s bridge from the tap to the service picking the intent up). Only when all three are false does a tap mean "connect"; do not key anything off `isRunning()` alone (the identity guard and Settings' "reconnect to apply" check `tunnelActive` too). The UI is not the guard, though — the service is: `ACTION_CONNECT` is ignored while `tunnelActive` (a second one used to establish a second tunnel, get "already running" from the shim, and take the error path into `shutdown()`), `connect()` re-checks after `establish()` and after `FipsNative.start()` that it has not been cancelled (`stillWanted`, a counter `shutdown()` bumps — Overview offers "tap to cancel" while connecting), and `rebindOnce` does nothing once `tunnelActive` is false, so a rebind queued before a Disconnect cannot bring the VPN back. Shutdown and connect are serialised: stopping the engine takes seconds on a phone (~5 s on a Pixel 9 Pro), so `shutdown()` takes ownership of its session's tun fd up front (it used to read `tunFd` at the END of its thread and closed a newer tunnel's fd, leaking the old one as an inert `tun0`), and an `ACTION_CONNECT` that arrives while `stopping` is queued and served by `finishShutdown()` on the same service instance — it used to run alongside the tail of the shutdown and be taken down by its `stopSelf()`. A Disconnect cancels a queued connect. `establishTunnel` counts the apps it actually allowed and falls back to capturing only fips2go when that is zero: a builder with no allowed application is a whole-device VPN, reachable before by uninstalling the only selected app. Settings' Save button is an extended FAB shown exactly while `hasUnsavedChanges()` holds (re-derived on every widget change, never a dirty flag) — a new persisted widget must be added to `SWITCHES`/`TEXT_FIELDS` as well as to `load`/`save`/`hasUnsavedChanges`. Snackbars and non-secret clipboard copies go through `Ui.snack`/`Ui.copy` (anchored above the bottom navigation; no duplicate "copied" toast on Android 13+); the nsec still goes through `OverviewFragment.copySecret` only.

Zero-config first run (0.3): a fresh install connects without the user opening Settings. `ConfigStore.applyDefaults()` — called from both `MainActivity.onCreate` and `FipsVpnService.onStartCommand`, since always-on VPN starts the service with no UI — seeds a bootstrap peer (`test-de01`) plus the toggle defaults, and deletes `RETIRED_KEYS`. It seeds only keys the user has never saved (`contains()`), which is what makes it safe on an upgrade: `SettingsFragment.save()` writes every key, so an existing choice — including a deliberately blanked field — is never overwritten. Nostr rendezvous and the in-app `.fips` resolver are now hardcoded on in `buildConfigJson`. Nostr is **not** peer discovery by default: the app leaves `node.rendezvous.nostr.policy` at fips's `configured_only`, so no peer the app did not configure is dialed from an advert — the configured set being the bootstraps and, with Settings → "Link directly to the servers of domains you use" (below), the servers of pinned public domains. Settings → "Discover peers via Nostr" (`nostr_discovery`, `DEF_NOSTR_DISCOVERY` = false) flips it to `policy: open` through the shim, which also sets both bounds to `nostr_discovery_max_peers` (default 3): `open_discovery_max_pending` (fips's own knob, the queue) and `open_discovery_max_peers` (fork knob @ 6c95f54/3a747ec, a ceiling on the overlay pool as a whole — queued + connecting + connected; sent from `DEF_NOSTR_DISCOVERY_MAX_PEERS`, which is also what the Settings summary quotes, so the number on screen and the bound in the node are one constant). The second exists because a queued peer leaves the queue when it connects, so `max_pending` alone bounds the growth *rate* and the only size bound was `max_peers` = 128; lowering `max_peers` instead would also cap LAN and inbound peers. It is a ceiling, not a set-point — nothing dials to reach it — and `0` in the shim means the default, not unlimited. What Nostr does on the phone: advertise the node, keep the relay connections the Overview card shows, and — since the shim sets `via_nostr` on every configured peer whenever Nostr is on (fips rejects it otherwise) — append a configured peer's advertised endpoints as fallback after its static address, so a bootstrap that moves is re-found. Links therefore come only from configured peers and mDNS: the one bootstrap the user picked plus, with `bootstrap_fallbacks` on (default), the first `FALLBACK_COUNT` of `FALLBACK_BOOTSTRAPS` whose npub differs from it (`ConfigStore.fallbackPeers`), so a single server outage does not empty the mesh; plus, with public names on and Settings → "Link directly to the servers of domains you use" (`names_direct_servers`, `DEF_NAMES_DIRECT_SERVERS` = true; sent as `names_server_peers` = `NAMES_DIRECT_SERVER_COUNT` (2) or 0), the servers of the most recently verified pins — DNSSEC or multi-resolver only, since a single resolver's answer must not make a node a permanent peer — which the shim reads from `names-pins.json` at each node start and adds as peers with no address and `via_nostr`, so fips dials them from their Nostr adverts (`config.rs` `pinned_servers`). A domain's server is usually several hops away and the mesh took up to 30 s to find one after a connect; a direct peer needs no discovery (device-verified: first lookup 0.25 s, 4 s after connecting). The cost is a kept-alive link each, the server's operator seeing the phone's IP and online times, and the public relays seeing which servers it links to — hence the switch. A server whose CNAME names another node still needs that node found; a pin made while connected becomes a peer at the next connect; STUN, transports and DNS upstreams are omitted entirely so fips uses its built-in defaults. Relays are omitted too **unless the user customised them** (`RelaysActivity`, opened from Overview's "Nostr relays" card): the list lives under the pref key `relay_list` — NOT `nostr_relays`, which is the pre-0.3 setting's name and sits in `RETIRED_KEYS`, so `applyDefaults` would delete it on every launch. An absent key means "never customised": nothing is sent and fips's built-in relays apply (and keep applying across pin bumps); `ConfigStore.DEFAULT_RELAYS` is only a display mirror of that fips default — check it against fips `src/config/node.rs` when bumping the pin. Every relay passes `ConfigStore.normalizeRelay` both when stored and again in `buildConfigJson`, because fips adds each one with `add_relay(..)?` — a single URL nostr-sdk rejects fails the node's whole Nostr bootstrap. The last relay cannot be removed (the shim reads an empty list as "defaults", so an empty editor would lie), the list is capped at `MAX_RELAYS`, and a change made while connected is applied like a mesh-app change: one `requestRebind()` on leaving the screen, since fips fixes its relay pool at node start. Settings keeps only everyday toggles at the top level, with peer npub/endpoint/transport, inbound ports, split tunnel, worker threads and log level behind a collapsed Advanced group. FIPS Hotspot defaults on, so `MainActivity` shows a one-time rationale before the fine-location prompt on the first connect (Settings' own prompt is now the follow-up path, not the only one) — it runs *before* the notification/battery-exemption prompts, which would otherwise stack a system dialog and a settings Activity over it.


## Constraints & gotchas

- `shim/.cargo/config.toml` forces 16 KB page alignment (`max-page-size=16384`) on `aarch64` and `x86_64` — required on Android 15+/Pixel 9-class devices; don't remove it. `armeabi-v7a` stays 4 KB (32-bit Android never uses 16 KB pages).
- Three ABIs are built; the **debug** APK packages all of them (`arm64-v8a`, `armeabi-v7a`, `x86_64`) while **release builds ship one APK per ABI plus a universal APK** carrying all three (`-PreleaseAbi` drives the release `abiFilters` and takes a comma-separated list — one ABI per per-ABI APK, the full list for the universal one; only `arm64-v8a` is device-verified). The universal APK is a first-install convenience for the release page only; the per-ABI APKs are what the updater consumes, and a partial `./release-build.sh <abi>` run skips the universal build rather than package stale `jniLibs/` output. The ABI list lives in three places that must stay in sync: `build-native.sh`, `rust-toolchain.toml`, and the debug `abiFilters` in `android/app/build.gradle.kts`. 32-bit `armeabi-v7a` is the build most likely to break on a fips pin bump (pointer-width casts — e.g. bionic's 32-bit `msghdr.msg_namelen` is `i32`); build it before bumping the pin.
- Releases: **`RELEASING.md` is the full step-by-step** (version decision, build, GitHub release, Zapstore publish, credential handling) — follow it rather than reconstructing the sequence. `./release-build.sh` (signs via gitignored `android/keystore.properties` → keystore at `~/.android-keys/fips-android-release.keystore`; unsigned fallback when absent). It archives an unstripped `.so` per release for symbolication and verifies ABI contents, 16 KB alignment, and the signature. Bump `versionCode` + `versionName` together. Versioning policy (adopted after 0.1.6; earlier releases bumped the patch digit for everything): pre-1.0 semver — **minor** (0.2 → 0.3) for new user-visible features, **patch** (0.2.0 → 0.2.1) for bug fixes/polish; **1.0** is reserved for the native npub-addressed API milestone (replacing the interim IPv6/TUN compat layer). `versionCode` stays a plain monotonic counter (+1 per release) independent of the name; the in-app updater compares dotted numerics, so differing segment counts (`0.2` vs `0.1.6`) are fine. `THIRD-PARTY-NOTICES.md` is generated from the arm64 `cargo tree` (no GPL links into the Android build — `rustables` is host-only) and must be regenerated on a fips pin bump. Installing a release over the debug build (or vice versa) requires an uninstall — different signing keys — which wipes app data **including the mesh identity**, since the nsec is sealed by a non-exportable Keystore key that dies with the uninstall and `allowBackup="false"` rules out `adb backup`. Since 0.3 this is survivable *if you plan ahead*: Overview → **Back up** reveals the nsec to copy, and **Restore** takes it back afterwards. There is still no way to recover an identity from a build that has already been uninstalled, and a device running a pre-0.3 build cannot back up at all — check what is installed (`adb shell dumpsys package org.fips.android`) and compare signers (`apksigner verify --print-certs`) before an uninstall.
- min SDK 26, target/compile SDK 34.
- **Always-on VPN is opted out of** (`android.net.VpnService.SUPPORTS_ALWAYS_ON = false` on the service, honoured from API 27). Android starts an always-on service with the bare `android.net.VpnService` action, which `onStartCommand` does not treat as a connect, so the service sat bound with no tunnel — and with "Block connections without VPN" on, the selected apps had no connectivity until the user opened the app and tapped connect (seen on a Pixel 9 Pro running 0.4.1). `applyDefaults()` is still called from `onStartCommand` because API 26 ignores the opt-out and can start the service with no UI. Supporting always-on for real means handling that start as a connect *and* the no-UI failure modes (no VPN consent yet, identity error) — do not just delete the meta-data.
- **Release asset names are load-bearing.** `Updater.kt` picks a GitHub release asset by suffix — `-<abi>.apk` and `-<abi>.apk.sha256` — which is exactly what `release-build.sh` emits into `dist/v<versionName>/`. Renaming or omitting either artifact silently breaks in-app updates for already-installed users (the check returns "no update"), and no later release repairs it, because the same mismatch recurs. This is why the universal APK is an *addition* rather than a replacement, and why its `-universal` suffix must keep matching no ABI — `release-build.sh` asserts that — or every client would pull 40 MB instead of its own ~18 MB APK. The updater downloads, verifies the sha256, and hands the APK to the system installer, which enforces the release signing key and refuses while the VPN is connected.
- Don't reinstall or force-kill the app while the VPN is connected — it can leak netd routing rules that block other apps' connectivity until reboot. Disconnect first.
- Launcher icon assets (`android/.../res/mipmap-*`) are generated from the fips repo's `docs/logos/fips_logo.png` (mesh graphic cropped, luminance→alpha, adaptive icon + monochrome layer).
- `PHASE1-NOTES.md` / `PHASE2-NOTES.md` / `PHASE3-NOTES.md` document the porting history and verification status — consult them before changing the embedding seam, but not for which sockets are protected or which fips hooks exist: Phase 2 and 3 describe hooks the app has since stopped using (each carries a note saying so), and the Socket protection bullet above is the current statement. Much of this codebase's behaviour is the result of a specific device-observed bug, and the commit message usually explains it: search history for a file before changing it.
